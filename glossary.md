# Глоссарий терминов — webserv

---

## Сеть и протоколы

### TCP/IP (Transmission Control Protocol / Internet Protocol)
Семейство протоколов, лежащих в основе интернета. IP TCP —  `webserv` используется TCP для приёма HTTP-запросов.
Стек протоколов, в который входят:
- **IP** (IPv4 или IPv6) — сетевой уровень, отвечает за маршрутизацию пакетов между хостами
- **TCP** или **UDP** — транспортный уровень, отвечает за надёжную потоковую доставку между приложениями
- HTTP, HTTPS, FTP, SSH и др. — прикладной уровень


### TCP (Transmission Control Protocol)
Надёжный потоковый протокол передачи данных. Гарантирует порядок доставки байт и отсутствие потерь. Важно: границ сообщений нет — `recv()` возвращает "сколько дали сейчас", а не "один запрос целиком". HTTP работает поверх TCP.

### IPv4
- **Адрес**: 32-битный (4 байта), записывается в виде четырёх десятичных чисел, разделённых точками.  
  Пример: `192.168.0.1`, `8.8.8.8`
- **Количество адресов**: ≈ 4.3 миллиарда (2³²)
- **Формат заголовка**: 20 байт (без опций)
- **Особенности**:
  - Самая распространённая версия до сих пор.
  - Адреса давно закончились → используется NAT (Network Address Translation).
  - Поддержка широковещательных адресов (Broadcast).

### IPv6
- **Адрес**: 128-битный (16 байт), записывается в виде восьми групп по четыре шестнадцатеричные цифры, разделённых двоеточиями.  
  Пример: `2001:0db8:85a3:0000:0000:8a2e:0370:7334`, `::1` (localhost)
- **Количество адресов**: 3.4 × 10³⁸ (2¹²⁸) — практически неисчерпаемо.
- **Формат заголовка**: 40 байт (фиксированный, упрощён по сравнению с IPv4).
- **Особенности**:
  - Встроенная поддержка IPsec (шифрование на сетевом уровне).
  - Нет NAT в классическом понимании (каждое устройство может иметь глобальный адрес).
  - Автоконфигурация (SLAAC).
  - Упрощённая маршрутизация.
  - Поддержка multicast вместо broadcast.

### Разница между IPv4 и IPv6

| Характеристика              | IPv4                              | IPv6                                      |
|----------------------------|-----------------------------------|-------------------------------------------|
| **Размер адреса**          | 32 бита                           | 128 бит                                   |
| **Количество адресов**     | ~4.3 млрд                         | ~340 ундециллионов                        |
| **Запись адреса**          | `192.168.1.1`                     | `2001:db8::1`                             |
| **NAT**                    | Обязателен в большинстве случаев  | Не требуется (но возможен)                |
| **Заголовок**              | Переменный (20+ байт)             | Фиксированный 40 байт                     |
| **Fragmentation**          | Выполняется маршрутизаторами      | Только отправителем                       |
| **Checksum в заголовке**   | Есть                              | Нет (проверка на транспортном уровне)     |
| **IPsec**                  | Опционально                       | Обязателен (но не всегда включён)         |
| **Broadcast**              | Есть                              | Заменён на Multicast                      |
| **Поддержка**              | Почти везде                       | Растёт (но всё ещё не везде)              |
| **Совместимость**          | —                                 | Dual-stack (IPv4 + IPv6 одновременно)     |

### HTTP (HyperText Transfer Protocol)
Протокол прикладного уровня для передачи гипертекста. Работает поверх TCP. Основан на схеме "запрос-ответ". Не сохраняет состояние между запросами (stateless).

```
GET /path HTTP/1.1\r\n
Host: localhost\r\n
\r\n
[body]
```
Структура ответа:
```
HTTP/1.1 200 OK\r\n
Content-Length: 5\r\n
\r\n
Hello
```
Заголовки от тела отделяются `\r\n\r\n`.

### HTTP/1.0 vs HTTP/1.1
- **HTTP/1.0**: соединение закрывается после каждого запроса.
- **HTTP/1.1**: keep-alive по умолчанию, заголовок `Host` обязателен, поддержка chunked encoding.

### HTTPS (HTTP Secure)
HTTP поверх TLS/SSL. Все данные шифруются: нельзя перехватить пароли, куки, содержимое страниц. Требует сертификат на сервере.

### RFC (Request for Comments)
Официальные технические спецификации интернет-протоколов. Для webserv важны:
- **RFC 1945** — HTTP/1.0 (проще, хорошая отправная точка)
- **RFC 7230** — HTTP/1.1 синтаксис
- **RFC 7231** — HTTP/1.1 семантика (методы, статус коды)

## HTTP — методы и статус-коды

### HTTP Methods (Методы запроса)

| Метод       | Описание                             | Типичное использование 
|-------------|--------------------------------------|------------------------
| **GET**     | Получить ресурс                      | Запрос страниц, файлов, API
| **HEAD**    | Получить только заголовки (без тела) | Проверка существования ресурса, кэширование
| **POST**    | Отправить данные на сервер           | Формы, загрузка файлов, создание ресурсов
| **PUT**     | Заменить ресурс целиком              | Обновление/создание ресурса 
| **DELETE**  | Удалить ресурс                       | Удаление файлов/записей
| **PATCH**   | Частичное обновление ресурса         | JSON Patch, частичное редактирование
| **OPTIONS** | Получить разрешённые методы сервераа | CORS, проверка возможностей

**Важные понятия:**
- **Безопасные методы** (`Safe`): не изменяют состояние сервера (GET, HEAD, OPTIONS).
- **Идемпотентные методы**: повторный вызов не меняет результат (GET, HEAD, PUT, DELETE, OPTIONS).

### HTTP Status Codes (Коды ответа)

#### 2xx — Успех
| Код  | Название                  | Описание
|------|---------------------------|----------
| 200  | OK                        | Стандартный успешный ответ
| 201  | Created                   | Ресурс успешно создан (POST/PUT)
| 204  | No Content                | Успех, но тело ответа отсутствует

#### 3xx — Перенаправление
| Код  | Название                  | Описание
|------|---------------------------|----------
| 301  | Moved Permanently         | Ресурс перемещён навсегда
| 302  | Found                     | Временное перенаправление
| 307  | Temporary Redirect        | Временное перенаправление с сохранением метода
| 308  | Permanent Redirect        | Постоянное перенаправление с сохранением метода

#### 4xx — Ошибка клиента
| Код  | Название                          | Описание
|------|-----------------------------------|----------
| 400  | Bad Request                       | Неверный запрос 
| 403  | Forbidden                         | Доступ запрещён 
| 404  | Not Found                         | Ресурс не найден 
| 405  | Method Not Allowed                | Метод не поддерживается 
| 413  | Payload Too Large                 | Слишком большой размер тела 
| 414  | URI Too Long                      | Слишком длинный URI 
| 431  | Request Header Fields Too Large   | Слишком большие заголовки 

#### 5xx — Ошибка сервера
| Код  | Название                  | Описание 
|------|---------------------------|----------
| 500  | Internal Server Error     | Внутренняя ошибка сервера 
| 501  | Not Implemented           | Метод не реализован 
| 502  | Bad Gateway               | Неверный ответ от upstream 
| 503  | Service Unavailable       | Сервер временно недоступен 

### Важные HTTP-заголовки

#### Заголовки запроса (Request Headers)
- `Host` — обязательный в HTTP/1.1 (имя сервера и порт)
- `User-Agent` — информация о клиенте
- `Accept` — желаемые MIME-типы ответа
- `Content-Type` — тип тела запроса (`application/json`, `multipart/form-data` и т.д.)
- `Content-Length` — размер тела в байтах
- `Connection: keep-alive / close`
- `Cookie` — куки клиента
- `Authorization` — авторизация

#### Заголовки ответа (Response Headers)
- `Content-Type` — тип содержимого ответа
- `Content-Length` — размер тела ответа
- `Content-Disposition` — имя файла при скачивании
- `Location` — куда перенаправлять (при 3xx)
- `Set-Cookie` — установка куки
- `Server` — информация о сервере
- `Date` — дата и время ответа
- `Connection: keep-alive / close`

### Content-Length vs Chunked Transfer Encoding

- **`Content-Length`** — точный размер тела в байтах. Сервер должен отправить ровно это количество.
- **`Transfer-Encoding: chunked`** — тело передаётся частями (chunks). Используется, когда размер заранее неизвестен (например, при генерации ответа на лету).

### Connection: keep-alive / close

- **`keep-alive`** (по умолчанию в HTTP/1.1) — соединение остаётся открытым для последующих запросов (существенно повышает производительность).
- **`close`** — после ответа соединение закрывается.

## Сокеты и файловые дескрипторы

### Socket (сокет)
Объект в ядре ОС для сетевого взаимодействия. Абстракция операционной системы для двусторонней коммуникации (по сети или между процессами). В Unix-подобных системах сокет — это **файловый дескриптор** (`fd`).
Основные системные вызовы для работы с сокетами:
- `socket()` — создание сокета
- `bind()` — привязка к адресу и порту
- `listen()` — перевод в режим прослушивания
- `accept()` — принятие входящего соединения
- `connect()` — подключение к удалённому серверу (для клиента)
- `recv()` / `send()` — чтение/запись данных
- `close()` — закрытие сокета

### FD (File Descriptor / Файловый дескриптор)
Целое положительное число, которое ядро ОС выдаёт процессу при открытии любого ресурса:
- `0` — stdin (стандартный ввод)
- `1` — stdout (стандартный вывод)
- `2` — stderr (стандартная ошибка)
- Начиная с `3` — пользовательские (файлы, сокеты, pipe, epoll и т.д.)

### Listen-сокет (пассивный сокет)
Сокет который только принимает входящие соединения. Создаётся цепочкой: `socket()` → `bind()` → `listen()`. На нём никогда не делают `recv()`/`send()` — только `accept()`.

### Client-сокет (активный сокет)
Возвращается `accept()`. Это двусторонний канал с конкретным клиентом — на нём делают `recv()` и `send()`.
### Важные параметры и вызовы

#### Backlog
Параметр функции `listen(socket, backlog)`.  
Определяет максимальный размер **очереди** входящих соединений, которые ядро может держать, пока сервер не вызовет `accept()`.  
Рекомендуемые значения: **128–512** (в Nginx по умолчанию 511).

#### `accept()`
- Извлекает первое соединение из очереди.
- Возвращает новый файловый дескриптор (client socket).
- В цикле событий обычно вызывается в цикле, пока не вернёт `-1` с `EAGAIN` (в неблокирующем режиме).

#### `recv()` и `send()`
- **Важно**: Эти функции **не гарантируют** чтение/запись всего запрошенного объёма данных за один вызов (**partial read/write** — это норма).
- Нужно всегда проверять возвращаемое значение и обрабатывать частичную передачу в цикле.

#### `bind()`
Привязывает сокет к локальному IP-адресу и порту.  
Часто используют `INADDR_ANY` (0.0.0.0) или `IN6ADDR_ANY` для прослушки на всех интерфейсах.

### Полезные опции сокетов (`setsockopt`)

**SO_REUSEADDR** - Разрешает мгновенное переиспользование порта после перезапуска сервера. Избавляет от ошибки `Address already in use`
**SO_REUSEPORT** - Позволяет нескольким процессам слушать один и тот же порт (полезно для многопроцессных серверов). Используется в современных серверах
**TCP_NODELAY** - Отключает алгоритм Nagle (полезно для низкой задержки). Часто включают в веб-серверах
**SO_KEEPALIVE** - Включает TCP Keepalive на уровне ядра. Помогает своевременно закрывать "мёртвые" соединения

### TIME_WAIT
Состояние TCP-сокета после **активного** закрытия соединения (когда первым отправлен `FIN`).  
Ядро держит сокет в этом состоянии примерно **2 минуты** (2×MSL), чтобы защититься от задержавшихся в сети пакетов.  

**SO_REUSEADDR** позволяет новому сокету сразу занять порт, даже если старые соединения всё ещё находятся в `TIME_WAIT`.

## Неблокирующий I/O

### Блокирующий vs неблокирующий режим
- **Блокирующий** (по умолчанию): `recv()`, `send()`, `accept()` приостанавливают процесс до завершения операции.
- **Неблокирующий** (`O_NONBLOCK`): если операция не может завершиться немедленно — возвращают `-1` с `errno = EAGAIN`.

### `O_NONBLOCK`
Флаг файлового дескриптора. Устанавливается через `fcntl(fd, F_SETFL, flags | O_NONBLOCK)`. Делает все I/O операции на fd немедленно возвращающимися. Обычно устанавливается сразу после accept() для client-сокетов и после socket() для listen-сокета.

### `fcntl()`
Системный вызов для управления параметрами fd. `F_GETFL` — получить текущие флаги, `F_SETFL` — установить новые.

### `EAGAIN` / `EWOULDBLOCK`
Эти два макроса обычно равны (на Linux). Значения `errno` при неблокирующей операции которая не может завершиться сейчас. Означает "Операция не может быть выполнена прямо сейчас, попробуй позже" — это не ошибка, это норма.

## I/O мультиплексирование

### I/O Multiplexing (мультиплексирование)
Техника наблюдения за несколькими fd одновременно в одном потоке, позволяющая **одному потоку** эффективно работать с большим количеством файловых дескрипторов (сокетов) одновременно. Вместо блокировки на каждом fd по отдельности — ждём события на любом из них.
Без мультиплексирования неблокирующий I/O почти бесполезен — пришлось бы постоянно опрашивать все сокеты в цикле (`busy polling`), что сильно нагружает CPU.

### Основная идея
Вместо того чтобы блокировать поток на одном `recv()` или `accept()`, мы говорим ядру:  
«Сообщи мне, когда на любом из этих дескрипторов можно читать или писать».

### Сравнение механизмов мультиплексирования

| Механизм     | ОС                  | Макс. fd     | Сложность | Производительность | Рекомендация |
|--------------|---------------------|--------------|-----------|--------------------|--------------|
| `select()`   | Все                 | 1024         | Низкая    | Плохая             | Не использовать |
| `poll()`     | Все                 | Неограничено | Средняя   | Средняя            | Для простых случаев |
| `epoll`      | Linux               | Миллионы     | Средняя   | Отличная (O(1))    | **Основной выбор** |
| `kqueue`     | macOS, FreeBSD      | Миллионы     | Средняя   | Отличная           | Аналог epoll |
| `IOCP`       | Windows             | —            | Высокая   | Отличная           | Для Windows |

### `poll()`
Системный вызов. Принимает массив `struct pollfd`, засыпает, просыпается когда на каком-либо fd произошло событие. Возвращает количество fd с событиями.

```c
int poll(struct pollfd *fds, nfds_t nfds, int timeout);

fds — массив структур pollfd
nfds — количество элементов в массиве
timeout — время ожидания в миллисекундах (-1 = бесконечно)
```

### `struct pollfd`
```c
struct pollfd {
    int   fd;       // дескриптор
    short events;   // что ждём (заполняем мы)
    short revents;  // что случилось (заполняет ядро)
};
```

### `POLLIN` / `POLLOUT` / `POLLERR` / `POLLHUP`
Флаги-биты для `events`/`revents`:
- `POLLIN` — можно читать (recv(), accept())
- `POLLOUT` — можно писать (send())
- `POLLERR` — ошибка на сокете
- `POLLHUP` — соединение разорвано.
- `POLLNVAL` — неверный fd

## Архитектура сервера

### Event Loop (событийный цикл)
Это **сердце** любого высокопроизводительного неблокирующего сервера (Nginx, Node.js, Redis и т.д.).
**Основная идея**: один поток (или несколько worker’ов) в бесконечном цикле ожидает событий через механизм мультиплексирования (`epoll`/`kqueue`/`poll`) и обрабатывает их.

Один поток обслуживает тысячи соединений.
Минимальное потребление CPU (нет busy-polling).
Предсказуемое поведение.

### State Machine (стейт-машина)
Объект переходящий между состояниями в зависимости от событий. В webserv: `Connection` имеет состояния `READING` → `WRITING` → `CLOSING`. Текущее состояние определяет поведение.

### Incremental Parser (инкрементальный парсер)
Парсер который работает с неполными данными. Получил кусок — обработал сколько смог — вернул состояние — жди следующего куска. `HttpRequest::parse()` именно такой.

### Partial Send
`send()` может отправить меньше байт чем запрошено — это норма. Поэтому ответ хранится в буфере `out_` и дожимается по частям при следующих `POLLOUT`.

### Virtual Hosts
Несколько сайтов на одном IP/порту. Различаются по заголовку `Host:` в запросе. В webserv — несколько `server {}` блоков на одном порту.

## Конфигурация

### nginx-like конфиг
Текстовый файл состоящий из блоков `{ }` и директив заканчивающихся `;`. Комментарии `# ...`.

### Директива
Команда конфига: `name arg1 arg2 ... ;`

### Контекст
Уровень вложенности в конфиге: top-level, server-контекст, location-контекст.

### `server {}` блок
Описывает один виртуальный сервер: на каком порту слушать, какой root, error pages и т.д.

### `location {}` блок
Правила для конкретного URI-префикса: методы, root, autoindex, CGI и т.д.

### Longest Prefix Match
Алгоритм выбора `location`: из всех совпадающих по префиксу location-блоков побеждает тот у которого самый длинный префикс.

### EffectiveConfig / ResolvedConfig
Итоговые настройки для конкретного запроса — результат слияния server-уровня и location-уровня. Location перекрывает server там где задан.

## Файловая система

### URI (Uniform Resource Identifier)
Путь в HTTP-запросе: `/images/photo.jpg`. Это не путь на диске — это логический адрес ресурса.

### URL (Uniform Resource Locator)
URI + схема + хост: `http://localhost:8080/images/photo.jpg`. URL — это конкретный вид URI.

### Root
Директория на диске которая является корнем сайта. Путь к файлу = `root + URI`.

### Index
Файл по умолчанию для директории. Если запрошена директория и есть `index.html` — отдаётся он.

### Autoindex
Листинг содержимого директории в виде HTML-страницы. Включается директивой `autoindex on`. Если выключен и index-файла нет — 403.

### Redirect (return)
Перенаправление клиента на другой URL. Ответ с кодом 301/302 и заголовком `Location:`.

### Error Pages
Кастомные HTML-страницы для ошибок. Задаются в конфиге: `error_page 404 /errors/404.html`.

### Path Traversal
Атака через `../` в URI для выхода за пределы root: `/../../etc/passwd`. Защита: проверять URI на наличие `..` компонент.

### URL Decode (percent-encoding)
URI может содержать символы закодированные как `%XX` где XX — hex-код символа. Например пробел = `%20`. Сервер должен декодировать URI перед маппингом на файловую систему.

### MIME Type / Content-Type
Тип содержимого файла. Определяется по расширению: `.html` → `text/html`, `.jpg` → `image/jpeg`, `.js` → `application/javascript`.

### `stat()`
Системный вызов. Возвращает метаданные файла/директории: тип, размер, права, время модификации. Используется для проверки существования файла и определения его типа.

### `S_ISREG()` / `S_ISDIR()`
Макросы над `st_mode`: проверяют является ли файл обычным файлом или директорией.

### `opendir()` / `readdir()`
Функции для чтения содержимого директории. Используются при генерации autoindex.

## CGI (Common Gateway Interface)

### CGI
Протокол запуска внешних программ для генерации динамического контента. Сервер запускает скрипт (`.php`, `.py`), передаёт ему запрос через переменные окружения и stdin, читает ответ из stdout.

### CGI переменные окружения
`REQUEST_METHOD`, `QUERY_STRING`, `CONTENT_LENGTH`, `CONTENT_TYPE`, `PATH_INFO`, `SCRIPT_FILENAME` и другие — передаются CGI-скрипту.

### Chunked Transfer Encoding
Способ передавать body без `Content-Length` — кусками с указанием размера каждого куска. Для CGI: сервер должен "раз-чанковывать" запрос перед передачей скрипту, и обрабатывать chunked-ответ от скрипта.

## Безопасность и надёжность

### Keep-Alive
Переиспользование TCP-соединения для нескольких HTTP-запросов. Уменьшает задержки. Требует корректного парсинга границ запросов в буфере.

### Slowloris
Атака: клиент очень медленно присылает заголовки, удерживая соединение и ресурсы сервера. Защита: таймаут на чтение заголовков + лимит размера (`maxHeaderBytes` → 431).

### `client_max_body_size`
Лимит размера тела запроса. Если `Content-Length` превышает лимит → 413 Payload Too Large.

### Zombie Connection
Соединение которое числится открытым но уже не активно. Происходит если не удалять fd из `connections_` при закрытии.

## Инструменты отладки

### `curl`
Утилита для HTTP-запросов из командной строки. `-v` показывает полный диалог заголовков.

### `telnet`
Позволяет вручную отправлять сырые HTTP-запросы и видеть сырые ответы байт в байт.

### `netcat` (`nc`)
Аналог telnet, удобен для скриптования тестов.

### `strace`
Трассировка системных вызовов процесса. Полезно для отладки зависаний и неожиданного поведения.

### `valgrind`
Детектор утечек памяти и ошибок работы с памятью.

### ASAN / UBSAN
Компиляторные санитайзеры. ASAN — утечки и out-of-bounds. UBSAN — undefined behavior. Включаются флагами `-fsanitize=address,undefined`.

Makefile — Relink Explained

Breve explicación del típico problema de cargo cult en 42. La gente realmente confunde:

  • relink
  • rebuild/recompile
  • dependency tracking

Y estas son tres cosas COMPLETAMENTE DISTINTAS, joder.

Vamos a desglosarlo con cuidado, porque aquí es importante entender la mecánica real de make, y no repetir conjuros como un chamán con un tambor. 😏

¿Qué es relink en realidad?

Relink es cuando se vuelve a ejecutar el comando de linking:

$(CXX) $(OBJS) -o $(NAME)

Es decir:

  • los archivos objeto ya existen,
  • pero el binario final se genera de nuevo.

¿Cuándo hace make un relink?

make solo mira los timestamps. Esta es la regla:

$(NAME): $(OBJS)
	$(CXX) $(OBJS) -o $(NAME)
Si cualquier $(OBJ) es más nuevo que $(NAME) → hay que relinkear.

Eso es todo. Sin magia.

¿Qué es un “relink innecesario”?

make
make
make

…y el linking se produce cada vez, aunque el código, los objetos y el binario estén actualizados. Esto es un bad Makefile.

La gran confusión de los alumnos del campus 😏

Hacen esto:

$(NAME): $(OBJS) Makefile includes.hpp
“Ahora el relink está arreglado”

NO, JODER.

Han añadido nuevas dependencias y aumentado la cantidad de situaciones en las que se ejecuta el linking. Han hecho casi lo contrario.

¿Qué hace realmente una dependencia de un header?

main.o: main.cpp includes.hpp
si includes.hpp ha cambiado → hay que recompilar main.o

Esto es una compile dependency.

NO es relink.

¿Por qué entonces ocurre relink después?

  1. se recompiló main.o
  2. su timestamp es ahora más nuevo
  3. $(NAME) es más antiguo que el objeto
  4. make ejecuta el linking
el relink es una CONSECUENCIA de la recompilación del objeto, no una dependencia directa del header.

El punto más importante

Un header no debe ser nunca una dependencia directa del binario.

$(NAME): $(OBJS) includes.hpp  ← esto suele ser incorrecto

El linker no lee headers — son para el compilador, no para el linker.

Modelo correcto

main.o: main.cpp includes.hpp
$(NAME): $(OBJS)

¿Por qué algunos añaden Makefile como dependencia?

$(OBJS): Makefile
“si cambian los flags de compilación → recompila todo”

Pero esto es compile invalidation, NO relink avoidance.

make es bastante tonto

make no entiende include graph, compile flags, ABI ni cambios semánticos. Solo sabe: target, prerequisites, timestamps.

Makefile minimal correcto

NAME = app
SRCS = main.cpp test.cpp
OBJS = $(SRCS:.cpp=.o)
CXX  = c++
CXXFLAGS = -Wall -Wextra -Werror

$(NAME): $(OBJS)
	$(CXX) $(CXXFLAGS) $(OBJS) -o $(NAME)

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

clean:
	rm -f $(OBJS)

fclean: clean
	rm -f $(NAME)

re: fclean all
all: $(NAME)
.PHONY: all clean fclean re

Versión production (recomendada)

CXXFLAGS += -MMD -MP
DEPS = $(OBJS:.o=.d)
-include $(DEPS)

Así los headers se rastrean automáticamente. Nivel adulto 😏

Makefile — Relink Explained

  1. Relink = the linker runs again ($(CXX) $(OBJS) -o $(NAME)). Happens when any .o is newer than the binary. Fix: write $(NAME): $(OBJS) correctly and don't put headers there.
  2. Recompile = a .o is rebuilt from source. Triggered when its .cpp or a tracked .hpp is newer. Fix: main.o: main.cpp includes.hpp.
  3. Dependency tracking = knowing which .o to recompile when a header changes. Best done automatically with -MMD -MP flags.
relink ≠ recompile ≠ dependency tracking
$(NAME): $(OBJS) includes.hpp ← wrong  |  $(NAME): $(OBJS) ← correct

Adding a header directly to $(NAME) does not fix relink — it increases how often linking runs. Classic cargo cult.

Что такое relink вообще?

Relink — это когда заново выполняется команда линковки:

$(CXX) $(OBJS) -o $(NAME)

То есть:

  • объектники уже существуют,
  • но итоговый бинарь собирается заново.

Когда make делает relink?

make смотрит на timestamps. Вот правило:

$(NAME): $(OBJS)
	$(CXX) $(OBJS) -o $(NAME)
Если любой $(OBJ) новее чем $(NAME) → надо перелинковать.

ВСЭ. Никакой магии.

Что такое «ненужный relink»?

Это когда ты запускаешь:

make
make
make

и линковка происходит каждый раз, хотя:

  • код не менялся,
  • объектники не менялись,
  • бинарь актуален.

Вот это bad Makefile.

А теперь главная путаница долбоёбов из кампуса 😏

Они делают так:

$(NAME): $(OBJS) Makefile includes.hpp
«Теперь relink исправлен»

НЕТ БЛЯТЬ.

Они не «исправили relink». Они добавили новые зависимости и увеличили количество ситуаций, когда линковка запускается. То есть сделали почти обратное.

Что реально делает зависимость от header?

main.o: main.cpp includes.hpp
если изменился includes.hpp → надо пересобрать main.o

Это compile dependency.

НЕ relink.

Почему потом происходит relink?

  1. пересобрался main.o
  2. timestamp у него стал новее
  3. $(NAME) стал старее объекта
  4. make запускает линковку
relink — это СЛЕДСТВИЕ пересборки объекта, а не зависимость от header напрямую.

Самый важный момент

Header вообще НЕ должен быть зависимостью бинаря напрямую.

$(NAME): $(OBJS) includes.hpp  ← это обычно неправильно

Линковщик не читает header, не использует header — header нужен компилятору, а не linker’у.

Правильная модель

main.o: main.cpp includes.hpp
$(NAME): $(OBJS)

Это чистая, логичная dependency graph.

Тогда зачем некоторые добавляют Makefile как dependency?

$(OBJS): Makefile
«если изменились флаги компиляции — пересобери всё»

Например, CFLAGS = -Wall стало CFLAGS = -Wall -Wextra. Объектники технически устарели. Поэтому зависимость от Makefile имеет смысл.

Но это compile invalidation, НЕ relink avoidance.

Ещё глубже: make вообще тупой

make не понимает: include graph, compile flags, ABI, semantic changes. Он знает только: target, prerequisites, timestamps. ВСЭ.

Что реально означает «Makefile shouldn’t relink»?

В контексте 42 обычно имеется в виду:

make
make

не должно выводить c++ objs... или linking..., если ничего не изменилось.

Как случайно ломают и получают relink всегда?

$(NAME):
	$(CXX) $(OBJS) -o $(NAME)

без зависимостей — правило always out-of-date. Или .PHONY на $(NAME) — это вообще ядерная ёбань 🤡

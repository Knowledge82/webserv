===================== 20.05
clientMaxBodySize и hasClientMaxBodySize


Решение A (правильное): двухфазный парсинг
Парсим только headers с header-limits
Определяем uri → выбираем location → вычисляем effective maxBody
Проверяем Content-Length против effective maxBody
Только потом читаем body
Это самый чистый вариант.

Решение B (достаточно для 42 MVP): проверка после COMPLETE
Ты парсишь body по server-level лимиту (или дефолту 1MB), а после COMPLETE уже сравниваешь request_.getContentLength() с location-level лимитом и отдаёшь 413.

Минус: если клиент пришлёт 1MB, а location лимит 100 байт — ты уже прочитал лишнее. Но для тестера это обычно ок.

Тебе важнее:

сделать быстро и пройти тест (решение B: проверка после COMPLETE), или
сделать архитектурно чисто (решение A: двухфазный парсинг в HttpRequest)
Я бы для 42 сделала B сейчас, а A — уже после рефактора (перед keep-alive), потому что keep-alive всё равно заставит тебя переосмыслить state machine парсера.

bool Connection::onReadable()
{
    if (!readFromSocket())
        return false;

    HttpRequest::State st = parseRequest();

    if (st == HttpRequest::ERROR)
        return handleParseError();

    if (st != HttpRequest::COMPLETE)
        return true;

    return handleCompleteRequest();
}

============================= 29.05

Copilot said: Правильнее всего “прилупашить” CGI **не внутрь `Server`
Правильнее всего “прилупашить” CGI не внутрь Server как отдельный зверинец, а как расширение Connection, а Server оставить тупым диспетчером pollfd → “кому событие”. Тогда сохраняется ваша текущая архитектура: Server ничего не знает про HTTP, а Connection знает протокол и решает, какие fd и какие события ей нужны.

Но чтобы Server мог poll()-ить не только clientFd, а ещё и cgi pipe fd, ему всё равно нужен способ понять: “этот fd принадлежит какому Connection и это stdin/stdout?”. Это делается аккуратно через небольшую таблицу маршрутизации fd → handler.

Ниже — самый прямой и чистый план под ваш код (C++98, Allman, без лишней магии). Это не готовый финальный код, но достаточно конкретно, чтобы ты быстро реализовал.

1) Где жить CGI: в Connection (как state machine + ресурсы)
Добавить в Connection поля
Минимальный набор:

Состояние верхнего уровня расширить:

READING (как сейчас)
CGI (новое: ждём завершения CGI I/O)
WRITING
CLOSING
Внутренние поля для CGI:

pid_t cgiPid_
int cgiStdinFd_ (write end pipe, parent пишет)
int cgiStdoutFd_ (read end pipe, parent читает)
std::size_t cgiInOffset_ (сколько body уже отправили)
std::string cgiOut_ (накопленный stdout CGI)
bool cgiStdinClosed_
bool cgiStdoutClosed_
long long cgiDeadlineMs_ или time_t cgiDeadline_ (таймаут на CGI)
возможно EffectiveConfig/LocationConfig*/копия нужных данных для сборки reply после завершения
Почему это правильно
Connection уже отвечает за “протокол” и имеет request_, out_, state machine.
CGI — это часть обработки запроса данного клиента, значит хранить это в Connection логично.
Server останется простым: poll() + dispatch.
README note (сразу): “CGI становится частью connection state machine; сервер мониторит CGI pipes через общий poll”.
